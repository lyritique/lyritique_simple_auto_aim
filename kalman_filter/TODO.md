  为什么 tick_ns = 10.0 注定会错

  戳的增量是“名义帧周期”，所以 等效 ns/tick 会随帧率变：

  ┌──────────────────┬───────────┬───────────┬──────────────┐
  │       模式       │   增量    │ 实际周期  │ 等效 ns/tick │
  ├──────────────────┼───────────┼───────────┼──────────────┤
  │ 60 fps（这次）   │ 16.671 ms │ 17.860 ms │ 10.71        │
  ├──────────────────┼───────────┼───────────┼──────────────┤
  │ ~160 fps（上次） │ ~6.25 ms  │ 6.31 ms   │ ≈10.15       │
  └──────────────────┴───────────┴───────────┴──────────────┘

  同一个常数不可能同时对上两个模式。config.hpp:63-66 那两条“实测已验证”之所以对得上，是因为 20/60 档当时真的跑满了 20/60——它验证的是“设定帧率＝实际帧率”这种理想情况，而这个相机达不到。

  这也解释了“崩溃非常稳定，每次都一样”：这个偏差和负载、和 GPU 抖动都无关，纯粹是 设定帧率/实际帧率 的比例。只要不修，lag 一定按固定斜率涨，涨到 1 s 被静音，涨到 2 s 超过 max_history_seconds
  姿态查不到、开始丢帧。

  顺带一个反证：这次 board yaw 从 91.65° 只走到 91.99°（相机静止），所以 lag 涨到 1 s，aim 输出一直是正常的（cmd 84~99°，dist 2.3~2.66）。lag 本身不崩，相机一动才崩。

  1. 立刻能用的：--camera-time-source host。但主机戳有 ±1 帧（17.9 ms）量化，20 rad/s 下就是一帧 20° 的抖动，能用但不好。

  2. 正解：让拟合斜率生效。 代码里本来就有（mvs_camera.cc:535-541），但被 config_.tick_ns > 0 挡死了：

  tick_ns 默认 10，CLI 又拒绝 <= 0（cli.cc:571），所以这条拟合路径永远走不到。加一个 --camera-tick-ns 0 或 --camera-clock-fit，让默认走拟合，拟合失败再回退
  10。现在取帧是阻塞的、没有积压，拟合结果会很干净：应该落在 10.71 附近。

  要注意的是：拟合只能修“平均速率”，修不了帧间抖动——因为戳本身就是帧号的线性函数，它表达不了真实的到达抖动。等效误差在 ms 级，比 6.7%/s 强太多。
